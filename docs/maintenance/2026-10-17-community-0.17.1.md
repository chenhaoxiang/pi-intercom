# 0.17.1-fork.1 community synchronization

## Source and retained behavior

Integrate exact community v0.17.1 at `ddf288186d4c40b8a54fbe8c0d136cbe4893a032` into fork main `2c5a30b77ee9ffaec9392d84b55f63628c3869be`. Version `0.17.1-fork.1` retains durable ask/reply routing, strict pending-ask/identity protection, message dedupe, human-first delivery, restart-stable addressing and existing repair ancestry.

Community fixes persist extension state on Windows using a writable fsync handle, bound stalled-peer write queues and select a meaningful bare-reply turn context. The framing import keeps both upstream MAX_FRAME_BYTES and the fork isPendingAsk validator.

A semantic conflict was caught by the unchanged fork integration test: when an ordinary message and an ask enter one turn, upstream's new ask-preferred current context discarded the ordinary-message context needed for an explicit reply. The integration keeps the newest ordinary context separately for explicit sender matching only, clears it at turn end/reset, and never lets it override a pending-ask match or ambiguity. Bare replies still prioritize pending asks. Both upstream and fork regression cases are retained; the imported ambiguity-message expectation names the fork's existing replyTo-or-to requirement.
